Commands and pipelines

A command is one step. Operators join steps into a line, and only the last result is sent to chat.

OperatorMeaningExample
|Pipe: the left result becomes the right command's input. Stops if the left fails. {{ p }}random 1-6 | echo you rolled {1}
&&Run the right side only if the left succeeded. {{ p }}var incr channel.deaths && echo oof
||Run the right side only if the left failed. This is how you handle errors. {{ p }}weather {arg.1} || echo no idea
( )Grouping, so an operator applies to a whole section. ( {{ p }}a || default 5 ) > channel.x
> and >>Store the result in a variable; >> appends. Only on success. {{ p }}random 1-100 > chatter.luck

Results carry three things: an exit code, a message (what chat sees) and data (structured values other commands can read as {1}, {1.celsius}). Failure codes are documented in the language reference.

A line runs at most {{ 8 }} commands, and nothing runs at all if any part of it fails a check first — a line either goes through as a whole or does nothing.

Roles and permissions

Roles are ranked. A command requires a role, and anyone whose rank reaches it may run the command.

{% for name, rank in roles %} {% endfor %}
RoleRankComes from
{{ name }}{{ rank }} {% if name in ("broadcaster", "moderator", "vip", "subscriber") %}Twitch badges{% elif name == "everyone" %}everyone in chat{% elif name in ("bot_admin", "bot_owner") %}the bot's own admin list{% else %}custom, created per channel{% endif %}

Channels can add their own roles between 1 and 99 — {{ p }}role create ambassador 40 — and grant them with {{ p }}role add ambassador @someone [duration]. A role above moderator (a lead moderator, say) is just a higher rank.

Change what a command needs with {{ p }}perm set <command> <role>, or allow exactly one role regardless of rank with {{ p }}perm allow.

A denial is silent. The bot doesn't announce that you can't use something; a channel can configure an on_denied callback if it wants a reply.

Cooldowns

Every command has two cooldowns, and both must be clear before it runs:

  • Shared — one bucket for everyone at the same role tier.
  • Personal — your own bucket.
{{ p }}cooldown set random everyone 10 30   # 10s shared, 30s personal
{{ p }}cooldown show random

The tier that applies is the highest-ranked rule your rank reaches, so a moderator can be exempt while viewers wait. Being on cooldown is silent, with an optional on_cooldown callback.

Turning things on and off

Commands are grouped into modules. A channel can switch a whole module or a single command:

{{ p }}module list
{{ p }}module disable games
{{ p }}cmd disable roll
{{ p }}cmd log roll invocations     # how much of its use is written to the log

Bot admins can add global to any of those to set the default everywhere. A globally disabled command can't be re-enabled by a channel — that's the kill switch. A disabled command answers exactly like an unknown one, so it doesn't leak that it exists.

Custom commands

Anyone can build a command out of the pieces above:

{{ p }}cc add hype echo {chatter.display} is hyped!
{{ p }}cc param hype 1 name=target type=user "who to hype"
{{ p }}cc describe hype gets the chat hyped
{{ p }}cc publish hype          # a moderator offers it to the channel
WhatHow
Use your ownImmediately, anywhere the bot is — it's your personal alias.
Share{{ p }}cc share hype on, then others {{ p }}cc link @you hype
Offer to a channel{{ p }}cc publish (moderator by default)
Change it{{ p }}cc edit, {{ p }}cc revert, {{ p }}cc versions
Stop itMods: {{ p }}cc disable / {{ p }}cc unpublish. Owner: {{ p }}cc rm

Edits are live. When you edit a command, every channel and every person using it gets the new version immediately. There is no pinning and no approval step, so linking or publishing someone else's command always answers with a warning saying exactly that.

A custom command runs as whoever typed it. Commands inside it are checked against their permissions, their cooldowns and their rank — never the author's. Publishing something can't hand anyone new powers.

Names resolve in this order: built-in → published in this channel → a pack published here → published globally → your personal alias. {{ p }}@name addresses your own alias directly, and a built-in can never be shadowed.

Packs and derived commands

A pack is a set of commands that belong together — a game, a toolkit — published and unpublished as one unit:

{{ p }}cc pack create blackjack
{{ p }}cc pack add blackjack hit stand deal
{{ p }}cc publish pack blackjack
{{ p }}module disable blackjack     # the pack name is its module name

Commands added to a pack later appear in every channel that published it, for the same reason edits are live: a channel accepted the pack, and the owner decides what's in it. Publishing refuses, and changes nothing, if one of the names is already taken in that channel.

A derived command is a custom command published globally by a bot admin, so it works in every channel without being published one by one. Built-ins (written in Python) are primitive; derived commands are written in this language and can be fixed live. A channel can always override a derived command with its own, or switch it off.

Variables

Values the bot remembers, in seven namespaces:

NamespaceBelongs to
chatter.xyou, everywhere the bot is
channel.xthe channel
channel.chatter.xyou, in this channel
publisher.xthe custom command's author
publisher.chatter.xyou, for that author's commands
publisher.channel.xthat author, in this channel
publisher.channel.chatter.xyou, for that author, in this channel
{{ p }}var set chatter.location Lisbon
{{ p }}var incr channel.deaths
{{ p }}var top channel.chatter.points
{{ p }}echo 1 > channel.deaths

Who may write what is the safety boundary for shared commands. Your own commands may write your spaces; a published command written by someone else may write their spaces, and may only touch the channel's if a moderator granted exactly that variable:

{{ p }}cc grant points channel.chatter.points   # and {{ p }}cc revoke to take it back

A grant follows the command, not the name it was published under, and it survives the author's future edits — which the reply says when you grant it.

All variables are readable by anyone. Don't store anything private in them.

Triggers, listeners and timers

{{ p }}trigger add raid echo welcome {event.user.name} and {event.viewers} raiders!
{{ p }}trigger listen \bhello\b => echo hi {chatter.display}
{{ p }}timer add 15m min_lines=10 jitter=2m echo remember to hydrate
  • Triggers run on channel events. The payload is in {event.*}, and the chatter is the event's user — the raider, the subscriber.
  • Listeners run on ordinary chat lines matching a regular expression, with captures in {match.1} and {match.name}.
  • Timers run on a clock. jitter= spreads them out, min_lines= keeps them quiet in a quiet channel, and only_live waits for the stream.

All three run at the rank of the moderator who created them, never higher, and go through the same checks as a typed command.

Raids, subs, resubs and gift subs work today. Channel point redemptions, follows and cheers need the broadcaster to connect the bot for the full tier; a trigger for those can be created now and starts working when that happens.

Word filter

{{ p }}filter add word badword           # masks it: ****
{{ p }}filter add word slur tag insult   # replaces it with [insult]
{{ p }}filter add regex \d{9,} block     # blocks the whole message
{{ p }}filter add allow scunthorpe       # an exception, for the obvious reason
{{ p }}filter test some text here

Matching ignores the usual tricks: case, accents, zero-width characters, full-width letters, leetspeak (b4d), repeated letters (baaaad) and separators (b a d, b.a.d). Regular expressions match the text as typed, so digits and punctuation still mean what they say.

The filter applies to everything the bot says, and to what people store — custom command names and bodies, variable values and trigger expressions are rejected rather than saved. Bot admins keep a global list that applies in every channel.

Moderation-aware replies

If the message that triggered a command is deleted, or its author is timed out or banned while the bot is still working, the run is cancelled and nothing is sent. The check runs before each command, before any side effect, and again immediately before sending. A channel can add reply_hold_ms to delay replies slightly, giving moderators a moment to act first.

Chat log and history

Every message is written to a searchable log (full-text). Nothing is ever deleted: a deleted message keeps its row and gains a deletion time, so the record of what happened stays honest. Timeouts, bans and chat clears are stored as events of their own.

Coverage is recorded too: the log knows exactly when the bot was listening. If the bot was down, the gap can be filled from the public recent-messages service when a channel opts in, and anything that can't be proven complete is marked partial rather than quietly called whole. Backfilled messages never run commands — they only go to the log.

Channels and onboarding

A broadcaster types {{ p }}join in the bot's own chat, and the bot starts reading and replying in theirs — no authorization needed for that. More becomes possible as trust grows:

TierWhat unlocks itWhat it adds
basicnothing — just {{ p }}joinreading chat, replying, commands, timers
moderatorthe broadcaster mods the botfollow events, moderation detail, higher send limits, no slow mode
fullthe broadcaster connects the botchannel point redemptions, sub and cheer events, the chat bot badge

{{ p }}part removes the bot; it stops listening and sending immediately.

Explaining an expression

{{ p }}explain {{ p }}random 1-6 | echo you rolled {1}
{{ p }}explain --run {{ p }}ping

Shows how each name resolved (built-in, published, or your alias, with the author and version), your rank against what each command requires, both cooldowns with the time remaining, which placeholders exist in that context, and the first check that would fail. --run also evaluates it, with variable writes discarded, cooldowns untouched and nothing sent to chat.

The admin pages show health, channels, and every channel's modules, triggers, filters, published commands and ignore list, with an audit trail of configuration changes. They need the local admin password and are meant for a LAN, not the internet.

The command reference and every channel page use the same table: one line per command, a search box that narrows it as you type (by name, alias, module, author or body text), and a click on any line for its arguments, cooldowns and examples. Press Esc in the box to clear it.
